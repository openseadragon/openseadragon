Tile loading: completion-paced scheduler vs. frame-paced loading

Both viewers open the same synthetic image through a simulated network: a browser connection pool (6 connections for HTTP/1.1, effectively unlimited streams for HTTP/2), a round-trip latency, a server with a fixed number of workers and a per-tile service time, and a link whose bandwidth is shared by every transfer in progress. Nothing touches the real network. Not modelled: tile decode cost on the main thread, packet loss, the 4 ms timer clamp and background tab throttling, and the frame rate of this machine, on which the frame-paced side depends. The left viewer uses the default serverProtocol: 'auto'; the right one is the previous frame-paced behaviour (serverProtocol: false, maxTilesPerFrame: 1). With "server sends Timing-Allow-Origin" the left viewer learns the protocol as it would from resource timing; without it, detection fails and the scheduler falls back to the HTTP/1.1 budget. Both viewers replay the same seeded sequence of zoom and pan hops, some of them faster than the animation can settle. "Time to cover" is measured from the start of a hop until the animation has settled and every tile the view needs is loaded; a hop interrupted before that counts as not covered.
